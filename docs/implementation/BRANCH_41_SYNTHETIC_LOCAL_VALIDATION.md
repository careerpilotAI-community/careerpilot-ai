# Branch 41 — Integrated Synthetic-Data Local Validation

**Status:** Operator-run validation procedure. No target Windows host, BitLocker state, NTFS ACL, Docker daemon, or local application instance has been inspected from this repository review. No readiness gate is marked passed by this document or by CI.

## 1. Purpose and boundaries

Branch 41 is the first integrated local validation milestone after the storage, deletion, backup, recovery-key, and security-verification work.

It validates the application with **synthetic data only** and records evidence for:
- clean local startup and PostgreSQL migration;
- local-profile authentication and session/CSRF behavior;
- synthetic resume upload, owner-scoped listing/download, and deletion;
- scanner fail-closed behavior in the non-local profile through the existing automated tests;
- private storage and deletion-journal path configuration;
- backup creation and isolated restore with current deletion-journal replay;
- the target host's encryption, recovery-key escrow, and NTFS ACL checks.

It does not authorize personal resume use, prove hosted readiness, or make the local development scanner a malware scanner.

## 2. Critical safety rules

1. Use only the synthetic PDF generated by `scripts/validation/New-SyntheticResume.ps1`. Do not upload a personal resume, another person's document, or a real job application artifact.
2. The `local` Spring profile enables registration and replaces ClamAV with a synthetic-fixture marker gate. It is strictly for synthetic tests. Never use it with real documents or expose it beyond loopback.
3. The fixture marker must be in the first 4 KiB. Ordinary PDFs are intentionally rejected by the local scanner.
4. Keep document storage, the deletion journal, and backup paths outside the Git repository and outside frontend/static directories.
5. Do not run destructive Docker commands such as `docker compose down -v` against any database containing data you need.
6. Do not restore over the active database, document root, or journal. Restore only to isolated targets.
7. Never record passwords, recovery passwords, resume content, emails, filenames, storage keys, or journal contents in the evidence report.
8. A passing local synthetic-data test is not approval for real-resume use.

## 3. Prerequisites and baseline

On the target Windows machine, verify:
- Windows 10/11 edition and supported BitLocker/Device Encryption capability.
- Java 21 JDK.
- Node.js 22+ and npm.
- Docker Engine/Desktop with Compose plugin.
- Git checkout at the intended merged `main` revision.
- PostgreSQL/Compose port 5432 available; backend 8080 and frontend 5173 available.
- A private local environment file created from `.env.example`; it is not committed.
- Separate absolute paths selected for document storage, the independent deletion journal, and backup storage.
- The data, journal, and backup volumes satisfy the approved BitLocker policy before relying on them for recovery.

Record only versions, drive letters/mount points, non-secret path labels, and status. Do not include secret values.

## 6. Synthetic fixture

Generate a valid one-page PDF containing the exact synthetic marker in a legal PDF comment:

```powershell
.\scripts\validation\New-SyntheticResume.ps1
```

The default output is under the current user's temporary directory. The script refuses to overwrite an existing file unless `-Force` is supplied. It contains no personal details.

If the PDF fails file validation or the synthetic marker is not detected, stop and investigate. Do not work around the guard by weakening the scanner or adding real content.

## 7. End-to-end functional checks

Use a private API client or browser session and synthetic-only values. Follow the authentication API documented in `docs/LOCAL_DEVELOPMENT.md`:

1. Fetch `GET /api/auth/csrf`.
2. Register two synthetic accounts with distinct reserved/example email addresses and strong throwaway passwords.
3. Log in as synthetic account A and retain its session cookie and CSRF token in the API client only.
4. Upload the generated synthetic PDF to `POST /api/resumes` as multipart field `file`, with kind `ORIGINAL`.
5. Confirm upload returns a safe metadata response and status `AVAILABLE`; confirm the scanner verdict is the local development fixture bypass, not a ClamAV clean verdict.
6. List assets as account A and download the uploaded asset. Compare the downloaded bytes with the generated fixture.
7. Log in as synthetic account B. Confirm B cannot list or download A's asset; the API should not disclose that the foreign asset exists.
8. Return to A, request deletion with a valid CSRF token, and confirm access is revoked before background cleanup finishes.
9. Wait for the deletion worker and verify the asset binary is absent from both quarantine and available storage and its metadata is finalized.
10. Confirm the sidecar journal contains the opaque asset-deletion tombstone. Inspect only whether the record exists and its schema/type; do not copy journal contents into the report.
11. Test logout and confirm the session is invalidated.

Also confirm malformed PDFs, unsupported extensions, oversized files, and ordinary PDFs without the synthetic marker are rejected. Do not use malware samples for this milestone.

## 8. Backup and isolated restore drill

Perform this only after the separate backup, document, and journal paths are configured and verified. The backup script requires BitLocker protection on all source volumes, a maintenance pause, and no unresolved deletion work.

1. Create a synthetic account A and upload the synthetic fixture. Record only opaque synthetic test identifiers locally, not in a public report.
2. Stop the API and all workers after queues are drained.
3. Run the daily backup procedure from `docs/architecture/storage/LOCAL_BACKUP_RESTORE_RUNBOOK.md`. Confirm a manifest is produced and every listed file hash validates.
4. Preserve the current independent deletion journal outside the backup directory.
5. After the backup, start the API, request deletion of the synthetic asset/account, and wait until the deletion tombstone is durably written. This creates a deletion newer than the selected recovery point.
6. Stop the API/workers and restore the selected recovery point into a separate database whose name contains `restore`, `recovery`, or `drill`, a new empty document root, and a new journal path. Use the current independent journal, not the older journal snapshot inside the backup.
7. Include `-ReplayDeletionJournal`. The restore script must refuse an unsafe or incomplete restore.
8. Verify the deleted synthetic account and its binaries are absent after replay. Verify a separate non-deleted synthetic account and its asset remain present, with owner-scoped access intact.
9. Keep the restored app stopped until every checklist item in the backup/restore runbook passes.

If any step is not feasible, mark the restore drill **NOT RUN** or **FAILED** with a non-sensitive reason. Do not infer a pass from successful backup creation, script parsing, CI, or manifest generation alone.
